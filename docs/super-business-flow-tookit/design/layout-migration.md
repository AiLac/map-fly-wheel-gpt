# 工具与项目数据目录迁移

本次按用户约定拆分旧 `docs/business-flow/`：工具根为 `docs/super-business-flow-tookit/`，项目数据根为 `docs/super-business-flow/`。`tookit` 使用指定拼写。`.cac` 中 Skill 名称和职责保持不变，业务 Git 仓库及临时运行根 `.temp/run/super-business-flow/<run-id>/` 不搬移。

拆分的目的是让工具升级只接触发行内容，保留本工程持续积累的配置和知识。继续使用一个根目录也可以按子目录区分，但安装者需要逐项判断更新范围；把工具安装到工作区外则可以共享版本，但会增加路径解析和版本配对。本次采用两个固定根目录，无需新增 Skill。

## 目录归属

| 旧 `docs/business-flow/` 下的内容 | 新位置 | 后续维护 |
| --- | --- | --- |
| `tools/`、`schemas/`、`templates/` | `docs/super-business-flow-tookit/` 下的同名目录 | 随工具版本更新 |
| `design/`、`examples/`、`README.md`、`deployment.md` | `docs/super-business-flow-tookit/` 下的同名路径 | 工具说明和固定示例随版本更新 |
| `project/`、`frameworks/`、`inventory/` | `docs/super-business-flow/` 下的同名目录 | 保留工程配置与已查证知识 |
| `mappings/`、`scenarios/`、`knowledge/`、`memory/`、`evidence/` | `docs/super-business-flow/` 下的同名目录 | 保留人工修订、当前结果及历史 |
| 自行添加且不在上表中的文件 | 先判定归属，再放入相应根目录 | 工具规范进入工具根，工程专属信息进入数据根 |

`examples/` 中随版本交付的输入和固定夹具属于工具包；重跑示例的扫描事实、图和发布结果写入数据根或独立 run。业务分析不回写工具目录，Maven 自身构建输出仍为 `tools/target/`。

## 迁移已有工作区

1. **保留现状与版本依据。** 记录旧工具提交，保存 `.cac` 中的本地修改、旧数据根、工作区配置和需要保留的 run。现有 Git 历史和原始数据可用于复查或回退；不要先删除旧目录。
2. **处理未完成任务。** 建议先用原工具版本完成未完成 run；也可保留旧检查点作档案，在新版本新建 run。本次没有实现跨布局检查点自动转换，不承诺旧状态可直接用新版本 `--resume`。
3. **按上表迁移。** 安装新版工具根，合入本工具的 `.cac` 文件；分类迁移已有工程目录到新数据根。保留人工覆盖、规则、配置、知识与记忆，不用新版本的初始数据覆盖它们。仍需使用旧版本完成任务时，先在保留的旧安装环境中完成，再切换当前安装。
4. **核对活动配置和引用。** 工作区根不变时，`repos[].path` 及业务源码位置通常不变。检查仓库配置中的 `classpath_file`、活动规则和证据引用、Markdown 跳转以及自动化命令是否仍指向旧目录。依赖清单搬到 `docs/super-business-flow/project/local/` 后，按新的位置重新生成并更新配置；注意 `classpath_file` 仍相对对应业务仓库根目录。
5. **重新查证派生产物。** 用新版本重新扫描所需入口，核验规则和映射采用的证据与源指纹，再按发布和记忆契约生成新的有效结果。路径发生变化可能影响配置或文件内容指纹，不能因为原内容看起来相同就跳过新鲜度检查。
6. **完成接入检查后清理旧布局。** 构建新工具，确认宿主发现 `.cac` 能力，用一个熟悉的入口核对数据写入位置、分支、代码链接和覆盖状态。确认旧目录中的自定义文件均有归属后再清理，保留历史回查依据。

路径改动分两类处理：当前可编辑的配置和文档入口可以明确更新；不可变历史 JSON、已发布版本、证据快照及其指纹不能做全局字符串替换。历史应保留原样，并保留能按原布局回查的旧提交或档案；通过新记录、重新扫描或新发布版本完成当前引用迁移。缺少原始证据时保留未决状态，不能制造“验证通过”。[发布契约](publication-contract.md)、[记忆契约](memory-contract.md)

## 迁移后的安装与升级边界

首次安装复制 `.cac` 的本工具集成以及两棵 `docs` 目录。日常升级只更新 `docs/super-business-flow-tookit/` 与 `.cac` 的 `super-business-flow*` 文件；保留 `docs/super-business-flow/`。若新版本变更数据 Schema，则依照该版本迁移要求处理，不能把目录隔离当成跨版本兼容保证。[Windows 部署步骤](../deployment.md)

合成示例可以按新布局重新生成证据、业务图和知识发布；旧示例保留在 Git 历史中，不通过伪造时间、指纹或原始路径让历史结果看起来已按新布局验证。

既有 [交付验证记录](validation-2026-09-11.md) 与其源码清单仅证明记录中对应的旧提交，不构成本次目录拆分的验收。新版应单独记录实际构建、测试、引用和示例发布结果；未执行的 Windows 宿主与真实 RPC 接入检查仍明确留待工程环境验证。
