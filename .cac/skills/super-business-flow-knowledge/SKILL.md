# 业务知识发布

主管 `docs/super-business-flow/knowledge/<scenario-id>/`。先读 [图与发布契约](../../../docs/super-business-flow-tookit/design/publication-contract.md)，按 [知识模板](../../../docs/super-business-flow-tookit/templates/knowledge/overview.md) 组织内容。只有生成新图时才加载 scenarios；不要为润色文档重扫所有仓库。

先校验图的节点/边/条件/证据引用和覆盖状态。证据必须指向真实源文件及校验指纹，或先保存到持久 evidence；不得仅引用 `.temp`。memory、Agent 摘要和重复转述不能充当原始代码证据。发布输出保留场景输入、代码版本、规则/映射版本和生成时间。

文档先说明业务目标、入口请求和返回，再概括关键阶段与分支。围绕一个关系画一张小图：业务图显示条件与返回；需要表达跨服务调用、异步汇合时再补服务时序图。用 `flowchart TD` 控制横向宽度，节点标签简短；解释放在图外。Mermaid 节点与稳定 graph ID 保持可追溯，使用表格存放详细代码链接。

v1 发布器生成持久源摘录及原源码相对链接，保留完整符号和行号。若项目另外提供 Git Web 链接策略，可由 Agent 核对后补充提交固定链接；不要声称 CLI 已实现任意链接模板。不同 Markdown 阅读器对本地行跳转支持不同，不能承诺所有编辑器均可定位行。未提交源码通过持久证据保留准确内容/指纹，不能把当前行号套到旧提交链接。

明确区分已确认事实、业务解读、未决边界与外部系统终点。图描述静态可达可能性；没有日志时不标注本次实际经过、耗时或命中频次。分支过多时拆子图并保留总览和索引，不裁剪分支来换取简洁。

使用发布工具验证并生成 Markdown；先把需要的业务文字汇入 graph.overview 等契约字段再发布。不可直接修改不可变版本目录；补充文案或图时形成新版本，业务结论仍要查证。由 `super-business-flow-reviewer` 抽查关键路径、RPC 目标、条件两侧、返回语义与代码链接。结构校验通过不等于业务正确。

未解决问题只能发布明确 `partial` 的文档并列出缺口；不能把“已生成文件”当完整分析。发布后只把跨场景关键发现与知识索引候选交给 memory，避免重复整篇文档。最终向开发者提供知识首页、输入范围、覆盖状态和最小待确认事项。
